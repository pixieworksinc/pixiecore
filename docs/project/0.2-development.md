# PixieCore 0.2 development

The `0.2.x` branch starts from `0.1.x` commit
`a39a18f39efdb7e3f44e32e5bb00d0ef73615d19`. The goal is to restore
[prompt-first POP](../specification/pop-principles.md): business behavior,
including deterministic rules, is executed by the LLM.

## Initial milestone

- Restore prompt-first terminology in the primary concepts, granularity, and
  Blueprint-authoring guides.
- Accept structured ordered Scenario/Role prompts alongside existing text.
- Keep normalized `Blueprint.prompt` text compatible with existing Role plugins.
- Publish a distinct experimental PixieCore v2 schema; preserve v1 explicitly.
- Add an LLM-executed Customer discount example and an 18-case evaluation dataset.
- Test delivery, invalid declarations, bindings, and semantic-error detection.

## Migration

Text prompts keep their existing decoding and binding behavior. No existing
Role plugin needs to parse a Scenario object: validation converts it to YAML
instruction text before plugin execution. Inner Role names are LLM reasoning
hints. Top-level `role` continues to select the registered message-preparation
plugin.

Editors loading `@pixieworks/pixiecore/blueprint/schema.json` receive the v2
schema on this branch. To retain the old editor contract, select
`@pixieworks/pixiecore/blueprint/v1-schema.json`. The archived portable POP 0.1
schemas and conformance suite continue to describe their original profile.

Existing host-composition examples are compatibility examples. They are not a
requirement to move deterministic policy out of prompts. Structural schema
checks, authorization, transport, persistence, and explicit side-effect handlers
continue to use ordinary runtime code.

## Next milestones

1. Run repeated real-provider Customer discount evaluations and compare text
   Role decomposition with structured Scenario instructions under the same
   model, input corpus, and sampling settings. Report observed errors as well
   as accuracy, latency, and cost.
2. Adapt the travel-approval and invoice examples so that complete business
   policies can be expressed in Blueprints; measure each proposed decomposition.
3. Review the remaining catalog, scaffold defaults, conceptual diagrams,
   comparison benchmarks, and optional JIT path against the restored principles.
4. Complete the portable-model RFC, independent evidence, and version/migration
   decisions without rewriting previously published POP identifiers.
5. Set the runtime package version and complete the normal release gates for a
   reviewed 0.2 candidate. Branch creation alone does not publish an npm release.

The package version stays at its inherited development value until release
preparation; neither a tag nor a published artifact is created by this milestone.
